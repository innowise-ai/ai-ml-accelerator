## The straight answer

No, don't ship a service account key JSON with the job. That's a long-lived, un-rotating credential — if it leaks (checked into git, left in an AMI, grabbed from EC2 instance storage, logged accidentally), anyone with it can read your GCS bucket and write to BigQuery from anywhere, forever, until someone notices and manually revokes it. For a workload running on AWS, there's a purpose-built alternative that avoids this entirely: **Workload Identity Federation (WIF)**.

## How it works

WIF lets your EC2 instance exchange an **AWS credential it already has** (its instance role, via the EC2 metadata service) for a **short-lived Google Cloud access token** — no Google credential ever has to be created, stored, or shipped.

Mechanism:
1. The batch job, running under an AWS IAM role attached to the EC2 instance, uses that role's temporary AWS credentials (fetched automatically from the instance metadata service) to sign a `GetCallerIdentity` request.
2. Google's Security Token Service (STS) validates that signed request against a **workload identity pool provider** you've configured to trust AWS.
3. STS returns a short-lived Google **federated token**, mapped to the AWS role's identity.
4. That federated token is used to **impersonate a Google Cloud service account** (via the IAM Service Account Credentials API), producing a short-lived Google access token.
5. Your code (Python/Go/etc. client libraries) uses that token like any other — it just needs to be pointed at a WIF credential config file via `GOOGLE_APPLICATION_CREDENTIALS`, and Application Default Credentials (ADC) handles the rest automatically.

The tokens are short-lived and refreshed automatically per-run — nothing static to leak, nothing to rotate manually.

## What to set up on the GCP side

1. **Create a Workload Identity Pool** — a container for external identities.
2. **Create an AWS provider** in that pool, configured with your AWS account ID. This tells Google to trust tokens signed by that AWS account's STS.
3. **Create (or choose) a Google service account** with least-privilege roles:
   - `roles/storage.objectViewer` (or a custom role scoped to just the one bucket) for reading GCS.
   - `roles/bigquery.dataEditor` scoped to the specific dataset, for appending rows. (Pair with `roles/bigquery.jobUser` at the project level if the job runs load/query jobs rather than streaming inserts.)
4. **Bind the AWS principal to that service account** with `roles/iam.workloadIdentityUser`, scoped down to the *specific AWS IAM role* the EC2 instance assumes (not the whole AWS account) — this is the step that prevents any AWS principal in your account from impersonating the GCP service account, only that one EC2 role can.
5. **Generate the credential config JSON** (`gcloud iam workload-identity-pools create-cred-config`) — this file contains no secrets, only routing/config info (pool, provider, target service account). It's safe to bake into the job's deployment artifact or bundle.

On the AWS side, you just need the EC2 instance to have an **instance profile / IAM role** — nothing exotic — since WIF calls `GetCallerIdentity` under the hood.

## Bottom line

Treat this the same as you'd treat any cross-cloud workload: identity federation, not static keys. Set up the pool + provider + scoped SA bindings once, ship the (non-secret) credential config with the job, and let ADC do the token exchange on every run.

## The mechanism: Workload Identity Federation (WIF) for AWS

GCP supports federating identity from AWS directly — no static credentials involved. The flow:

1. Your EC2 instance already has an **AWS IAM role** attached (instance profile), which gives it a way to sign requests (via the instance metadata service / `AWS_ACCESS_KEY_ID` etc., normally used to call `sts:GetCallerIdentity`).
2. Google's client libraries (via **Application Default Credentials**, ADC) detect the AWS environment, use that IAM role to construct a signed `GetCallerIdentity` request, and send it to Google's Security Token Service (STS).
3. Google's STS validates the AWS signature against the **Workload Identity Pool / AWS provider** you configured, and issues a short-lived Google STS token.
4. That token is used to **impersonate a Google service account** (via `iam.serviceAccounts.getAccessToken`), which mints a short-lived (1 hour) OAuth access token scoped to that service account's permissions.
5. Your job uses that access token like any other GCP credential — GCS and BigQuery client libraries handle this transparently if ADC is configured correctly.

No long-lived secret ever leaves Google or gets stored on the EC2 box. The AWS IAM role is the only "credential," and it's already scoped to the instance via the instance profile — nothing to leak from disk.

## What to set up on the GCP side

1. **Workload Identity Pool** (`gcloud iam workload-identity-pools create`) — a container for external identities.
2. **AWS provider** inside that pool (`gcloud iam workload-identity-pools providers create-aws`) — pass your AWS account ID. This tells Google to trust `GetCallerIdentity` calls signed by that account.
3. A **Google service account** the job will impersonate, with minimal permissions:
   - `roles/storage.objectViewer` (or a custom role) scoped to the specific bucket, not project-wide
   - `roles/bigquery.dataEditor` scoped to the target dataset, plus `roles/bigquery.jobUser` at the project level (needed to run load/insert jobs)
4. An **IAM binding** granting `roles/iam.workloadIdentityUser` on that service account to the specific AWS principal — scope this to the exact IAM role ARN of your EC2 instance profile, not the whole AWS account, e.g.:
   ```
   principalSet://iam.googleapis.com/projects/.../workloadIdentityPools/POOL/attribute.aws_role/arn:aws:sts::ACCOUNT:assumed-role/YOUR-EC2-ROLE
   ```
5. A **credential config JSON** (generated by `gcloud iam workload-identity-pools create-cred-config`) — this is *not* a secret. It just contains the pool/provider resource names and STS endpoint URLs. You point `GOOGLE_APPLICATION_CREDENTIALS` at this file and ADC does the rest.

## Should you ship a service account key JSON?

No. Don't do it. Concretely:

- It's a **long-lived, bearer credential** — anyone who reads that file (disk snapshot, backup, misconfigured S3 bucket, EBS volume reused later, log accidentally capturing it, insider with instance access) has full access until you notice and revoke it. There's no built-in expiry.
- It **has to be distributed and rotated manually** — baked into an AMI, pulled from Secrets Manager at boot, whatever — and every one of those paths is a place it can leak or go stale.
- It **decouples the credential from the machine** — the key works from anywhere, not just your EC2 instance, so compromise isn't contained to "someone got shell on this box."
- Google and AWS both are explicitly nudging away from this pattern; WIF exists precisely to eliminate the "download a key file" step for cross-cloud workloads like yours.

WIF costs you a bit more one-time setup (pool, provider, IAM binding, cred config) but after that the job "just authenticates" using the EC2 role it already has, tokens are short-lived and auto-rotate, and you can revoke access instantly by removing the IAM binding — no key to hunt down and delete across every instance/AMI/backup that might have a copy.

This is exactly the "change history" feature — the `CHANGES` table-valued function.

## What to turn on

Change history isn't captured by default. You need to enable it per table:

```sql
ALTER TABLE `my_project.my_dataset.my_table`
SET OPTIONS (enable_change_history = TRUE);
```

Once enabled, BigQuery starts retaining row-level change metadata going forward (it's not retroactive). There's also an `APPENDS` function for insert-only tracking, but that doesn't require this option — you specifically need `enable_change_history` because you also want updates and deletes.

## The query

```sql
SELECT
  *,
  _CHANGE_TYPE AS change_type,
  _CHANGE_TIMESTAMP AS change_time,
  _CHANGE_IS_FOR_UPDATE AS change_is_for_update
FROM
  CHANGES(
    TABLE `my_project.my_dataset.my_table`,
    '2026-09-17 00:00:00',
    '2026-09-18 00:00:00'
  );
```

Key output columns:
- **`_CHANGE_TYPE`** — `INSERT`, `UPDATE`, or `DELETE`. This is what you'll branch on to apply upsert/delete logic downstream.
- **`_CHANGE_TIMESTAMP`** — commit time of the transaction, useful for ordering/watermarking your next window's start.
- **`_CHANGE_IS_FOR_UPDATE`** — `TRUE` when a `DELETE` row is actually the "old" half of an update (BigQuery represents an update as a delete of the old row + insert of the new row). You can generally ignore these delete-of-update rows and just apply the `UPDATE`/`INSERT` rows, or use it to distinguish "real" deletes from update churn if your downstream apply logic needs that distinction.

## Practical notes for your nightly job

- Track the end timestamp of each run as the start timestamp of the next, so windows are contiguous.
- There are limits on how far back you can query change history and on unsupported table types (e.g., certain views, some external tables) — worth checking the current limits doc before committing to this, since retention window affects how much slack you have if a run fails.

```sql
SELECT
  _CHANGE_TYPE,
  _CHANGE_TIMESTAMP,
  * EXCEPT (_CHANGE_TYPE, _CHANGE_TIMESTAMP)

  TIMESTAMP '2026-09-17 00:00:00 UTC',
  TIMESTAMP '2026-09-18 00:00:00 UTC'
)

```

```sql
SELECT device_id, metric_name, ts, value

```

**What actually avoids the full scan**

1. **Partition the table** on `DATE(ts)` (or ingestion time). The `WHERE ts >= ...` predicate then prunes partitions before any data is read — this is the single biggest lever.
2. **Cluster on `(device_id, metric_name, ts)`**. Clustering sorts data within partitions, so filters/joins on those columns skip blocks instead of reading everything. It doesn't prune as hard as partitioning, but it helps a lot with the window function's partition-by.
3. **The recency filter is the real trick.** `ROW_NUMBER` over the whole table is only cheap if you've already restricted the input rows via partition pruning. MERGE `project.dataset.latest_readings` T
```sql
USING (
  SELECT device_id, metric_name, ts, value
  FROM `project.dataset.telemetry`
  WHERE ts > @last_merge_ts        -- partition-pruned, only new rows
  QUALIFY ROW_NUMBER() OVER (PARTITION BY device_id, metric_name ORDER BY ts DESC) = 1
) S
ON T.device_id = S.device_id AND T.metric_name = S.metric_name
WHEN MATCHED AND S.ts > T.ts THEN UPDATE SET ts = S.ts, value = S.value
WHEN NOT MATCHED THEN INSERT (device_id, metric_name, ts, value) VALUES (S.device_id, S.metric_name, S.ts, S.value)
```

For "latest row per group" in BigQuery, the query pattern matters less than the table's physical layout — no SQL trick avoids scanning bytes that aren't pruned by partitioning/clustering. Two things to get right:

**1. Table layout**

Partition by day on `ts`, cluster by `(device_id, metric_name)`:

```sql
CREATE TABLE `project.dataset.telemetry` (
  device_id STRING,
  metric_name STRING,
  ts TIMESTAMP,
  value FLOAT64
)
PARTITION BY DATE(ts)
CLUSTER BY device_id, metric_name;
```

This lets BigQuery prune partitions by date and skip clustered blocks that don't match a `device_id`/`metric_name` filter — that's what actually avoids the full scan, not the query shape.

**2. Query shape**

Avoid the classic self-join (`JOIN (SELECT device_id, metric_name, MAX(ts) ...) ON ...`) — it scans the table twice. Use one of these instead, both single-pass:

```sql
-- ARRAY_AGG with per-group LIMIT — BigQuery can compute this without fully
-- sorting each partition, generally the cheaper option
SELECT
  device_id,
  metric_name,
  latest.ts,
  latest.value
FROM (
  SELECT
    device_id,
    metric_name,
    ARRAY_AGG(STRUCT(ts, value) ORDER BY ts DESC LIMIT 1)[OFFSET(0)] AS latest
  FROM `project.dataset.telemetry`
  WHERE ts >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)  -- partition pruning
  GROUP BY device_id, metric_name
)
```

```sql
-- QUALIFY + ROW_NUMBER — more readable, but requires a full sort per partition
-- so it's typically a bit more expensive than the ARRAY_AGG form above
SELECT device_id, metric_name, ts, value
FROM `project.dataset.telemetry`
WHERE ts >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
QUALIFY ROW_NUMBER() OVER (PARTITION BY device_id, metric_name ORDER BY ts DESC) = 1
```

The `WHERE ts >= ...` bound is what triggers partition pruning — without it, BigQuery has to scan every partition even with clustering. Pick a window wide enough that every device/metric is guaranteed to have reported at least once (e.g. if devices report at least daily, 2-3 days is safe); if some devices go silent for long stretches, you'd need a fallback query with a wider window for the rows that come back NULL.
